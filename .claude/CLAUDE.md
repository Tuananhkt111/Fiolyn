# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Fiolyn is a .NET 10 web API with two responsibilities:

- **Telegram ingest** — receives webhook messages, resolves the sender's Telegram user ID to an `AppUser` via `AppUser.TelegramId` (no match → skip), saves the raw message as a page in a Notion database, and parses `stock buy/sell/div` commands into stock transaction records scoped to that `AppUser`.
- **Web REST API** — exposes CRUD endpoints for the personal-finance web app (stock transactions, broker accounts, and user-owned spend accounts), authenticated via Google SSO + Fiolyn-signed JWT.

**User model:** `AppUser` rows are created on first Google login, gated by an admin-managed `AllowedEmail` whitelist. Admins (`AppUser.IsAdmin = true`) can manage the whitelist and other users' roles.

**Repo layout:** `Fiolyn/` (app) · `Fiolyn.Tests/` (tests) · `docs/` (setup, plans).

**Stack:** C# 14 on .NET 10 · Northflank (Docker) · GitHub Actions → GHCR · Neon PostgreSQL · EF Core 10 · Notion API · Telegram Bot API · Google Sign-In · xUnit 2 · NSubstitute 5 · FluentAssertions 6

## Architecture

**Layered:** Controller (thin) → Service (business logic) → `IRepository<T>` (generic CRUD + composable queries) → `AppDbContext` → Neon Postgres.

- **Services** live in `Services/External/{Telegram,Notion,Google}/` for external integrations and `Services/Internal/` (implementations) + `Services/Internal/Interfaces/` (interfaces). Controllers inject interfaces. Services throw on errors — `Infrastructure/GlobalExceptionHandler` maps `KeyNotFoundException` → 404, `UnauthorizedAccessException` → 401, `ForbiddenAccessException` (project type in `Infrastructure/Exceptions/`) → 403, everything else → 500, and never leaks exception messages.
- **Repository** is generic (`IRepository<T>` in `Data/Repositories/`). Don't build entity-specific repositories.
- **Entities** implement `IAuditable` (Created/LastModified autopopulated on `SaveChangesAsync`) and usually `ISoftDelete` (`IsDeleted` flag). `RefreshToken` is the exception — revocation is explicit via `RevokedAt`, not soft-delete.
- **DI** is auto-discovered via `IServiceRegister` implementations in `ServiceRegisters/`, ordered by `Order`. Add new business services to `ScopedBusinessServicesRegister`. Use typed `AddHttpClient<TInterface, TImpl>` for HTTP clients (see `NotionServiceRegister`) — **don't** wrap with `AddSingleton<TInterface>(sp => sp.GetRequiredService<TImpl>())`, that pins one `HttpClient` forever and defeats `IHttpClientFactory` handler rotation.
- **Migrations do NOT apply on startup.** Run `dotnet ef database update` from `Fiolyn/` locally, and ensure the equivalent runs as part of deploy (Northflank release step or a pre-start command) before the app boots — the app will fail on any query against an un-migrated schema. DbSet names are singular and match the entity class (`StockTransaction`, not `StockTransactions`).

**Auth:** see **`.claude/rules/auth.md`** for the flow and rules.

## Code Style

- **Formatting** is enforced by `.editorconfig` — 2-space indent (no tabs), Allman braces, max 120 chars/line, spaces inside parens (`public class Foo( ILogger logger )`, `if ( x > 0 )`, `method( arg )`), LF line endings, UTF-8, trailing newline, trimmed trailing whitespace.
- **Naming (enforced as `:error`):** PascalCase for public members, constants, and types; `_camelCase` for private fields (e.g. `_signingKeyBytes`); `I` prefix for interfaces (`IRepository`, `IJwtService`); `Async` suffix for `async`-keyword methods (`GetByIdAsync`).
- **File-scoped namespaces** required (`namespace Fiolyn.Services ;` — not block-scoped). Enforced as `:error`.
- **Braces required** on all `if` / `else` / `for` / `while` bodies — no single-line bodies. Enforced as `:warning`.
- **Primary constructors** (C# 12+) required for DI. `public class Foo( ILogger logger ) { }`.
- **`field` keyword** (C# 14) for auto-properties that need setter logic — don't hand-roll a backing field. Pattern: `public string Email { get ; set => field = NormalizeEmail( value ) ; } = string.Empty ;`. See `AppUser.Email`, `AllowedEmail.Email`, `StockTransaction.Symbol`.
- **Extension members** (C# 14) — use `extension( ClaimsPrincipal principal ) { ... }` blocks, not a static class of `this`-parameter methods. See `ClaimsPrincipalExtensions`.
- **`record` for DTOs** — one class per file, file name matches class name.
- **`var` when the type is apparent** (`:suggestion`). `async`/`await` for all I/O — never `.Result`/`.Wait()`. Sync methods for non-I/O repo ops (`Attach`, `Update`, `Delete`).
- **XML docs:** only on public endpoint methods. On interface implementations use `/// <inheritdoc />` — don't copy the interface `<summary>`.
- **JSON:** camelCase response keys (global `CamelCasePropertyNamesContractResolver` in `WebApiServiceRegister`).

## Key Rules

### HTTP / controllers

- **`TelegramController` always returns 200.** Telegram retries non-2xx; every other controller uses proper status codes (201 Created, 200 OK, 204 NoContent, 404 NotFound).
- **Never return raw entities** from REST controllers. Use `record` DTOs in `Controllers/DTOs/Responses/{Resource}/`. Use request records in `Controllers/DTOs/Requests/{Resource}/` with `[Required]` / `[MaxLength]` annotations.
- **Refetch through the service's read method when a write response reads through a nav.** Two cases trip this:
  - *Create:* `AddAsync` + `SaveAsync` populates only the FK; the nav reference is null. See `StockTransactionController.CreateAsync`.
  - *Update where an FK actually changed:* the in-memory nav on the tracked entity is the *old* one — EF doesn't refresh it when you reassign the scalar FK, so the response would echo stale nav data (e.g. old `BrokerAccount.Name` after a broker reassignment). Capture the old FK before mutating, compare to the request value, and refetch only when it changed — the rename-only case (FK unchanged) keeps the prefetched nav and skips the refetch. See `BrokerAccountController.UpdateAsync` and `StockTransactionController.UpdateAsync` for the conditional pattern.
  The generic `IRepository<T>.GetByIdAsync` does *not* eager-load — service-layer read methods do (e.g. `StockTransactionService.GetByIdAsync` calls `.Include( t => t.BrokerAccount )`). Go back through the service before building the response DTO. (Updates that touch only scalar columns — e.g. `SpendAccountController.UpdateAsync` — don't need a refetch since no nav is read.)
- **User-owned resources: enforce ownership in the service, not the controller.** When a resource belongs to a specific `AppUser` (has an `AppUserId` FK), give the service user-scoped methods (`GetAllForUserAsync(userId)`, `GetByIdForUserAsync(id, userId)`, `SoftDeleteAsync(id, userId)`) that filter by `AppUserId` and treat "not owned by caller" as 404. Controllers pipe `User.GetUserId()` into every call.
- **Shared / multi-member resources: membership = access.** When a resource can be shared across users (no direct `AppUserId` FK, joins via an `Xxx`/`XxxMember` table), user-scoped reads filter by membership: `.Where(r => r.Members.Any(m => m.AppUserId == userId && !m.AppUser.IsDeleted))`. "Not a member" is still 404, same as the single-owner case. Management endpoints for the member list (add by email, remove, list) live on the user controller and require the caller to be a member. The `GetMembersAsync` / `AddMemberAsync` / `RemoveMemberAsync` methods bake the caller-membership check *into* the same query that fetches the data (target user, member list, count) — one round-trip instead of a separate `Ensure...` precondition query. `GetMembersAsync` uses `.Include(a => a.Members).ThenInclude(m => m.AppUser)` rather than a `Select`-projection so the response DTO can read `m.AppUser.Email` / `DisplayName`; `AddMemberAsync` / `RemoveMemberAsync` only need the FK columns and stay on the lighter `Select` projection. See `SpendAccount` / `SpendAccountMember` / `SpendAccountService` and `BrokerAccount` / `BrokerAccountMember` / `BrokerAccountService`.
- **Transitive access for child resources.** When a child resource (e.g. `StockTransaction`) is owned by a shared parent (e.g. `BrokerAccount`), the child has no direct `AppUserId` or `Members` — access flows through the parent's membership. User-scoped reads on the child filter `.Where(c => c.Parent.Members.Any(m => m.AppUserId == userId && !m.AppUser.IsDeleted))`. For writes, prefer to inline the same membership filter into a single combined query that *also* projects whatever else the write needs (FK columns, related-entity scalars), rather than issuing a separate `EnsureUserIsParentMemberAsync` roundtrip — null result → 404, regardless of whether it was the row or the membership that's missing. Membership-resolving subqueries belong on the *child's* service, not the parent's — avoids a DI cycle. See `StockTransactionService.{Create,Update}Async` for the combined-query pattern.
- **Admin cross-user endpoints go in a separate `Admin<X>Controller`.** Route `/api/admin/<resource>`, `[Authorize(Policy = AuthConstants.AdminPolicyName)]` at class level, and the *same* service interface — add admin methods (no user scoping, usually with eager-loading for owner/member enrichment, e.g. `.Include(a => a.Members).ThenInclude(m => m.AppUser)`). See `AdminSpendAccountController` / `AdminBrokerAccountController` vs `SpendAccountController` / `BrokerAccountController`. The split avoids both response-shape overloading and policy-per-action sprawl.
- **Trusted-internal ingest bypass: name the method, don't nullable the arg.** When a background path (e.g. cron) genuinely can't identify a caller, expose a dedicated service method like `CreateFromCronAsync(entity)` rather than making `userId` nullable on the user-scoped `CreateAsync`. Document it as "for trusted internal callers only" in the interface XML docs. The Telegram ingest no longer qualifies — `TelegramMessageService` now resolves the sender to an `AppUser` via `AppUser.TelegramId` and calls the user-scoped `CreateAsync(tx, userId)`; there is currently no live example of this bypass in the repo.
- **Telegram ingest is gated by `AppUser.TelegramId`.** Linking is self-service (`PUT/DELETE /api/users/me/telegram-id`) or admin (`PUT/DELETE /api/users/{id}/telegram-id`); the column has a unique index and duplicate attempts surface as 409 via `ConflictException`. Stock writes over Telegram still go through `IStockTransactionService.CreateAsync` and so inherit the existing broker-membership check.
- **All balance changes flow through `TransactionBase` and its leaves.** Abstract base + seven TPT children: `IncomeTransaction`, `ExpenseTransaction`, `LendTransaction`, `BorrowingTransaction`, `TransferTransaction`, `AdjustmentTransaction`, `StockTransaction`. The signed `Amount` on the base is what gets applied to `SpendAccount.Balance` (negative = money out, positive = money in). Sign is enforced server-side per leaf (Income +; Expense −; Lend −; Borrowing +; Transfer source − / destination +; Adjustment as-supplied; Stock via `StockTransaction.ComputeAmount` — Buy negative, Sell/Dividend positive). The unsigned stock trade total is not a stored column; it's `Math.Abs(Amount)` on the way out. Atomic writes go through `Services/Internal/Helpers/TransactionBalanceWriter.SaveWithConcurrencyGuardAsync` — load the tracked `SpendAccount`(s), mutate `Balance`, single `SaveAsync`; `[ConcurrencyCheck]` on `Balance` makes concurrent writers race, the loser surfaces a 409 `ConflictException`. The simple five (Income/Expense/Lend/Borrowing/Adjustment) share `StandardTransactionServiceBase<T>`; `TransferTransactionService` is its own class with the two-side membership check and dedupes balance deltas before saving. `Stock` keeps its own service for the broker-membership rule.
- **Per-kind access:** stock writes gate on `BrokerAccount` membership; everything else gates on `SpendAccount` membership; `Transfer` requires membership of **both** source and destination. The unified `GET /api/transactions` (`TransactionReadService.GetAllForUserAsync` / `GetAllAsync(userId)`) reads the union: member of the row's `SpendAccount` OR — for `TransferTransaction` rows — member of the `DestinationSpendAccount` OR — for `StockTransaction` rows — member of the `BrokerAccount`. Membership of the destination alone is enough to see a transfer; without that branch a user who only co-owns the destination would never see incoming transfers.
- **`TransactionCategory` is admin-managed and bound to one `TransactionKind` per row** (`Income | Expense | Lend | Borrowing | Transfer | Adjustment | Stock`). Unique index on `(Kind, Name)` so the same name is allowed across kinds. `Kind` is immutable post-create; each leaf service rejects mismatched `CategoryId` with 400 `BadRequestException` via the shared `TransactionCategoryGuard.EnsureKindMatchesAsync(categoryRepository, categoryId, expectedKind)` helper in `Services/Internal/Helpers/` — call it from every new leaf, don't reimplement the projection. Endpoints: `GET /api/transaction-categories?kind=…` (all authenticated users, read-only) and `GET/POST/PUT/DELETE /api/admin/transaction-categories?kind=…` (admin CRUD).
- **`Counterparty` is per-`AppUser` (private contact list).** `LendTransaction.CounterpartyId` and `BorrowingTransaction.CounterpartyId` are required FKs (`OnDelete.Restrict`); the legacy free-text `CounterpartyName` no longer exists on either leaf. Both leaves implement the marker interface `IHasCounterparty` (`Entities/IHasCounterparty.cs`) and inherit from `CounterpartyTransactionServiceBase<T>` (`Services/Internal/Helpers/CounterpartyTransactionServiceBase.cs`), which sits between `StandardTransactionServiceBase<T>` and the leaf service — the leaf class is reduced to a `Kind` override only. The wire contract still names the field `counterpartyName` on `LendTransactionRequest` / `BorrowingTransactionRequest` — `CounterpartyTransactionServiceBase.CreateAsync(tx, userId, name)` calls `CounterpartyResolver.ResolveOrCreateAsync(counterpartyRepository, name, userId)` (in `Services/Internal/Helpers/`) before delegating to the standard base, which case-insensitive-matches an existing row owned by the caller or stages a new one in the same `SaveAsync` (assign `tx.Counterparty = resolved`, never `tx.CounterpartyId = resolved.Id`, so EF threads the parent ID through for newly-staged rows). `CounterpartyTransactionServiceBase.UpdateAsync` short-circuits the resolver round-trip when the inbound name (case-insensitive, trimmed) matches the loaded `transaction.Counterparty.Name` — so PUTs that don't touch the counterparty don't pay the lookup. Supplying a *different* name resolves to a different counterparty — the original row stays put, it does not rename in place; that's what `PUT /api/counterparties/{id}` is for. SpendAccount co-members can read the counterparty's *name* via the eager-loaded `Counterparty` nav (the base's `BuildReadQuery` chains `.Include(nameof(IHasCounterparty.Counterparty))`; `TransactionReadService.BuildQuery` adds polymorphic includes via the `(t as LendTransaction)!.Counterparty` pattern), but only the owner can rename or soft-delete a `Counterparty`. Per-user case-insensitive uniqueness is enforced by a Postgres expression index `UNIQUE (AppUserId, LOWER(Name))` (raw SQL in the migration; not modelled in EF) — the service maps `23505` to `ConflictException` and pre-checks for the common case. Soft-delete is blocked while any active lend/borrow row references it (`CounterpartyService.EnsureNotReferencedByActiveTransactionAsync` → `BadRequestException`). The Counterparty soft-delete query filter is `!c.IsDeleted` only — **don't** also gate on `!c.AppUser.IsDeleted`, or eager-loaded navs on transactions read by co-members null out and crash the response builder.
- **No more `POST /spend-accounts/{id}/balance-adjustments`.** Manual deltas now go through `POST /api/adjustment-transactions` (or the admin twin) — `AdjustmentTransaction` accepts a signed `amount` (every other transaction request also names the field `amount`; for Adjustment alone the value is signed and skips the `[Range(1, long.MaxValue)]` constraint), gets a `Date`/`Description`/`Payer`, and inherits the same atomic write pattern.
- **Every `BrokerAccount` references a `SpendAccount` (NOT NULL FK).** Setting/changing `BrokerAccount.SpendAccountId` requires the caller to be a member of *both* accounts (`BrokerAccountService.EnsureUserIsSpendAccountMemberAsync`). The user-scoped service method is `UpdateAsync(id, userId, name, spendAccountId)` — it loads the tracked entity, performs the spend-membership re-check only when the FK changed, mutates, saves, and refetches via `GetByIdForUserAsync` when the FK changed so the response carries the fresh `SpendAccount` nav. Admin overload `UpdateAsync(id, name, spendAccountId)` skips the per-user check and only validates that the new spend account exists when the FK actually changed (rename-only updates skip the lookup). Returns null when the broker isn't found / caller isn't a member; controllers map that to 404. Soft-deleting a `SpendAccount` is blocked while any active broker references it (`SpendAccountService.EnsureNotReferencedByActiveBrokerAsync` → `BadRequestException`) **or** any active `TransactionBase` references it via `SpendAccountId` or `TransferTransaction.DestinationSpendAccountId` (`EnsureNotReferencedByActiveTransactionAsync`).
- **`Balance` is not part of `PUT /spend-accounts/{id}` or its admin twin.** PUT updates only `Name`/`Type` via `SpendAccountService.UpdateAsync(id, [userId,] name, type)` — the service does the load+mutate+save in one place; the controller is a pure HTTP adapter that just passes scalars and maps null→404. The PUT path intentionally **does not call `repository.Update(entity)`** — that would mark every column modified and emit an UPDATE that clobbers any concurrent balance write (and stomps the `[ConcurrencyCheck]` `WHERE Balance = @original` predicate). The service relies on EF's per-property change tracking on the already-tracked entity (loaded via `GetByIdForUserAsync` / `GetByIdAsync`). For every transaction `UpdateAsync`, the controller still mutates the tracked entity from `GetByIdForUserAsync` in-place and the service never calls `repository.Update(transaction)`, relying on EF's change tracker to detect the mutations alongside the balance write in a single `SaveAsync`.
- **Refresh-token rotation is single-flight.** `RefreshToken.RevokedAt` carries `[ConcurrencyCheck]`, so EF generates `UPDATE … WHERE Id=@id AND RevokedAt IS NULL` for the rotation. Two concurrent `/auth/refresh` calls on the same token race for the row; the loser's `SaveChanges` throws `DbUpdateConcurrencyException` and the same transaction rolls back the new `RefreshToken` it just staged. `AuthService.RefreshAsync` catches the exception and surfaces 401 — never silently issue parallel children. Don't reach for `ExecuteUpdate` here; the mock-based tests can simulate the loser by stubbing `_refreshTokens.SaveAsync().ThrowsAsync(new DbUpdateConcurrencyException())`.
- **Map Postgres `23505` (unique-violation) to `ConflictException`.** Pre-checks ("is this email/TelegramId taken?") narrow the common case; the unique index is the actual race-safe guarantee. When `SaveAsync` throws, catch `DbUpdateException` whose inner is `Npgsql.PostgresException { SqlState: PostgresErrorCodes.UniqueViolation }` and rethrow as `ConflictException` so the caller gets a clean 409 instead of a 500. Live examples: `UserService.UpdateTelegramIdAsync`, `AllowedEmailService.CreateAsync`.
- **Soft-delete filtering is enforced by global query filters, not by repository methods.** `AppDbContext.OnModelCreating` registers `HasQueryFilter(e => !e.IsDeleted)` for every `ISoftDelete` entity (`AppUser`, `AllowedEmail`, `SpendAccount`, `BrokerAccount`, `StockTransaction`) plus the transitive cases (`BrokerAccountMember`, `SpendAccountMember`, `RefreshToken` filter on `AppUser.IsDeleted`). `IRepository.Query()` therefore returns filtered rows by default — there is no `QueryActive()` variant; chain `.IgnoreQueryFilters()` if you genuinely need soft-deleted rows. `IRepository.GetByIdAsync` is a thin `FindAsync` wrapper and bypasses the filter (use `GetByIdOrThrowAsync` when "must be active" is part of the contract). The filter also applies through `.Include` chains and navigation traversals (`b.Members.Any(m => ...)`, `Select(b => b.Members.OrderBy(...).ToList())`), so don't write redundant `!m.AppUser.IsDeleted` predicates — they double the filtering, mislead readers, and only lined up with mock-test data anyway.
- **`Repository.SoftDelete` / `Restore` mark only `IsDeleted` modified.** They use `dbContext.Entry(entity).Property(IsDeleted).IsModified = true` instead of `Set<T>().Update(entity)`, so the generated UPDATE touches only `IsDeleted` (and `LastModified` via the `IAuditable` hook in `SetDefaultValues`) — no risk of clobbering a column another transaction wrote between this load and save.

### Auth

- **`Jwt:SigningKey` is mandatory, ≥32 chars.** App fails fast at startup (both `AuthServiceRegister` and `JwtService` ctor throw `InvalidOperationException`).
- **Admin bootstrap is manual** — insert `AllowedEmail`, log in once, `UPDATE AppUser.IsAdmin = true`. No code path auto-promotes.
- See **`.claude/rules/auth.md`** for the full auth rules (token rotation, claim constants, email normalization, `User.GetUserId()`, `AppUser` vs `User` collision).

### EF / repositories

- **`IRepository<T>` surface:** `Query()` (composable `IQueryable`, soft-deletes filtered via global query filter), `GetByIdAsync` / `GetByIdOrThrowAsync`, `AddAsync` / `InsertRangeAsync`, `Attach` / `Update` / `UpdateRange`, `Delete` (hard) / `SoftDelete` / `Restore`, `SaveAsync`. Compose via `Query()` when you need filters/projections; use the `GetById*` variants for single-entity fetches.
- **Use `GetByIdOrThrowAsync` when "not found" is an error** — it throws `KeyNotFoundException` (→ 404 via `GlobalExceptionHandler`). Use `GetByIdAsync` only when the caller needs to branch on null. Both filter soft-deleted rows; reach for `Query().IgnoreQueryFilters()` if you genuinely need a deleted row (rare). None of these eager-load — add `.Include(...)` in the service layer when you need navs.
- **`.AsNoTracking()` on read-only list paths only** — chain it before `.ToListAsync()` in `GetAllAsync` methods that project straight to DTOs. **Don't** add it to `GetByIdAsync` / `GetByIdForUserAsync` paths; callers fetch-then-mutate-then-update, and `SoftDeleteAsync` reuses the same fetch to load the row it then attaches. A detached entity from an `Include`-bearing read forces `MarkIsDeletedModified` to call `Attach`, which walks the nav graph and tries to re-track the included `SpendAccount` — but a `FindAsync` from the write path has already tracked a *different* instance with the same key, and EF throws `InvalidOperationException: another instance with the same key value … is already being tracked`. The same trap fires when a shared read helper (e.g. `BuildReadQuery` in `StandardTransactionServiceBase` / `TransferTransactionService`) bakes `.AsNoTracking()` into the query — every single-row consumer inherits it silently. Keep the helper tracking-on and chain `.AsNoTracking()` on the list call sites instead.
- **`Select`-projecting a collection nav doesn't fan out into its further navs.** `Select(b => b.Members.OrderBy(...).ToList())` materializes `BrokerAccountMember` rows but leaves `m.AppUser` null — projections only pull what you name in the projector. If the consumer reads a downstream nav (e.g. `BrokerAccountMemberResponse` reads `m.AppUser.Email`), use `.Include(b => b.Members).ThenInclude(m => m.AppUser)` and sort in memory after materialize, or extend the projector to assign `AppUser = m.AppUser` explicitly. See `BrokerAccountService.GetMembersAsync` / `SpendAccountService.GetMembersAsync`.
- **Hoist `.ToLowerInvariant()` out of EF LINQ predicates.** Compute the normalized comparand into a local first, so only the column-side call ends up in the translated expression tree: `var lowered = name.ToLowerInvariant(); ... b.Name.ToLower() == lowered`. See `StockTransactionService.ResolveBrokerAsync`.
- **`IQueryable` predicates can't use `is T x` pattern bindings.** Expression trees support the bare type-test `t is T` plus an explicit cast `((T)t).Nav`, but not the variable-binding form `t is T x` (CS8122 — "expression tree cannot contain pattern-matching `is` expression"). Polymorphic filters in EF therefore look uglier than in-memory C#: `t is StockTransaction && ((StockTransaction)t).BrokerAccount...`. Don't try to "clean it up" with `is T x`. See `TransactionReadService.GetAllForUserAsync`.
- **When a child references a parent staged in the same transaction, set the nav, not the scalar FK.** A freshly-`AddAsync`-ed parent has `Id == 0` until `SaveChangesAsync` round-trips to the DB, so `child.ParentId = parent.Id` persists `0` and hits a FK violation (`23503`). Use `child.Parent = parent` — EF fills in the FK after the parent insert within the same transaction. See `AuthService.IssueTokensAsync` assigning `RefreshToken.User = user` on first-time Google login. Children attached to the parent's collection nav (`parent.Members.Add(child)` before `AddAsync(parent)`) follow the same rule implicitly — EF threads the generated parent ID through to the join-table insert. See `SpendAccountService.CreateAsync`.
- **For explicit many-to-many join entities, prefer data annotations over `OnModelCreating`.** Use `[PrimaryKey(nameof(A), nameof(B))]` for composite keys and `[Index(nameof(B), nameof(A))]` for the reverse-lookup index (the PK's leftmost column leaves the other direction as a seq scan). Join rows that represent presence, not mutable state, should skip `IAuditable`/`ISoftDelete` — a single manually-set timestamp like `JoinedAt` is enough; leaving means hard-deleting the row. See `SpendAccountMember` and `BrokerAccountMember`.
- **`StockTransaction.Symbol` auto-normalizes** to uppercase via the setter. Don't manually `ToUpperInvariant()` on assignment.
- **Money and quantity fields are `long`, not `decimal`.** The primary currency is VND, which has no fractional subunit, and VN exchanges trade in whole-share lots. Applies to balances, prices, totals, quantities — entity, DTO, and `Parse` layer. See `SpendAccount.Balance`, `StockTransaction.{Quantity,Price}`, `TransactionBase.Amount`. Only reintroduce `decimal` if a genuine sub-unit requirement appears (confirm first).
- **Migrations:** never `EnsureCreated()` (bypasses migrations, corrupts history). Never edit or delete applied migrations — create a new down migration instead. To undo an *unapplied* migration, use `dotnet ef migrations remove`, not hand-deletion.

### Deployment (Northflank)

- **Do NOT use `UseHttpsRedirection`.** Northflank's reverse proxy sends plain HTTP; redirect causes request failures.
- App listens on port 8080 (`ASPNETCORE_URLS=http://+:8080`). Northflank terminates TLS externally.
- Push to `master` → GitHub Actions builds `Fiolyn/Dockerfile` (context = repo root) → pushes to GHCR → Northflank auto-deploys. GH Actions secret: `NORTHFLANK_API_TOKEN`.

### Workflow

- **After every code change:** call `mcp__ide__getDiagnostics` if available (else run `dotnet build` from the repo root) to catch compile/analyzer errors, then run **only the test classes covering the files you touched** via `--filter`, e.g.
  `dotnet test Fiolyn.Tests/Fiolyn.Tests.csproj --filter "FullyQualifiedName~AuthServiceTests|FullyQualifiedName~AuthControllerTests"`.
  Map each changed production file to its `*Tests.cs` (e.g. `AuthService.cs` → `AuthServiceTests`; a new `Controllers/FooController.cs` → `FooControllerTests`). Only fall back to the full suite (`dotnet test Fiolyn.Tests/Fiolyn.Tests.csproj`) when the change is cross-cutting (e.g. `IRepository<T>`, `AppDbContext`, `ServiceRegisters/*`, shared base classes) **or** as the pre-commit gate — all tests must pass before committing.
